## 1. Application functionality

Sentinel-IR is a cybersecurity incident-reporting platform built as three independently
containerised microservices behind a single API gateway. A security analyst logs in through
`auth-service` to receive a JWT, lists the organisation's registered infrastructure from
`asset-service`, raises an incident against one of those assets in `incident-service`, and then
tracks that incident through its severity levels (`LOW` → `MEDIUM` → `HIGH` → `CRITICAL`) and its
lifecycle (`OPEN` → `TRIAGED` → `RESOLVED`). Every request enters through the Kong API Gateway on
port 8000, which validates the token, applies rate limiting and stamps a correlation ID onto the
request before routing it; each service owns a private PostgreSQL database and reaches the others
only over HTTP. Every security-relevant action emits a structured JSON event on a fixed schema, so
one analyst's complete workflow can be reconstructed across all three services from a single
correlation ID, which is what makes the system useful as a data source for the SOC monitoring and
knowledge graph work in Phase 2.

## 2. API documentation

**Base URL:** `http://localhost:8000/api/v1`

Every endpoint below is reached through the gateway at that base URL. The direct service ports
(8001–8003) are exposed for inspection only and are not part of the public API. Interactive
OpenAPI documentation is generated by FastAPI at `/docs` on each service port.

### 2.1 All endpoints

**auth-service**

| Method | Endpoint URL | Auth | Purpose |
|---|---|---|---|
| POST | `/api/v1/auth/login` | public | Exchange credentials for a JWT |
| GET | `/api/v1/auth/verify` | bearer | Validate the current token and return its claims |
| POST | `/api/v1/auth/users` | bearer, admin | Create a user |
| GET | `/api/v1/auth/users` | bearer, admin | List users |

**incident-service**

| Method | Endpoint URL | Auth | Purpose |

| Method | Endpoint URL | Auth | Purpose |

| Method | Endpoint URL | Purpose |

### 2.2 Conventions

Paths are plural nouns. Status codes are used consistently: `200` read, `201` created, `204`
deleted, `400` malformed, `401` no or bad token, `403` wrong role, `404` unknown id, `409`
conflict, `422` validation failure naming the offending field, `429` rate limited. Every error
response uses one shape (`{"error": "<CODE>", "message": "<one sentence>", "details": {...}}`),
and every request and response carries an `X-Correlation-ID` header.

## 4. The two patterns implemented

The API Gateway is deliberately not claimed here, as the mark schedule excludes it.

### Pattern 1: Database per Service

Each service owns its data store exclusively; no service reads another's tables, and cross-service
data moves over HTTP.

**How it is implemented.** `deploy/docker-compose.yml` defines three separate PostgreSQL
containers (`auth-db`, `incident-db` and `asset-db`), each with its own credentials and its own
volume. Each service receives exactly one `DATABASE_URL` environment variable and has no knowledge
of any other connection string. Where `incident-service` needs asset information it stores an
`asset_id` and a snapshot of the asset name, never a foreign key into `asset-db`, so the two
schemas can change independently. Database access in each service is confined to its own
`app/repositories/` module.

**Why it holds.** A schema change in `asset-db` cannot break `incident-service`, because
`incident-service` has never seen that schema; it sees a JSON contract over HTTP. Either service
can be redeployed or migrated without coordinating with the other.

**Proof in the demo.** Connecting to `incident-db` and listing its tables shows no asset table at
all; the absence is the proof that no cross-schema read is possible. Then `docker compose stop
asset-db` degrades `asset-service` while `auth-service` and `incident-service` keep serving
normally.

### Pattern 2: Circuit Breaker with Retry

A caller wraps a remote dependency: transient failures are retried with backoff, and once failures
pass a threshold the breaker opens and returns a fallback immediately without touching the network
until a cooldown allows a trial call.

**How it is implemented.** `incident-service` needs `asset-service` when an incident names an
asset. That call goes through `libs/common/http_client.py` and nowhere else. Retry uses `tenacity`
with exponential backoff for connection errors and 5xx responses; the breaker uses `pybreaker`
with a failure threshold and reset timeout, both read from configuration (`CIRCUIT_FAIL_MAX`,
`CIRCUIT_RESET_SECONDS`, `RETRY_MAX_ATTEMPTS`, `RETRY_BACKOFF_SECONDS`). The declared fallback
returns an `AssetSummary` marked `available=False`, so an incident is still created, degraded
rather than failed. Three implementation decisions matter:

1. **Retry nests inside the breaker**, as `breaker(retry(one GET))`. A request retried three
   times and still failing counts as *one* failure against the threshold, not three. Nested the
   other way, a threshold of three would trip on the retries of a single request.
2. **Only transient faults count.** A connection error, timeout or 5xx is the dependency faulting.
   A `404` is a correct answer from a healthy service, so it propagates unretried and never counts
   toward opening the breaker.
3. **The client is long-lived**, cached per dependency URL. The breaker's failure count is the
   pattern's state; a client rebuilt on every call would count to one, never reach its threshold
   and never open.

**Proof in the demo.** With `asset-service` stopped, the first calls retry visibly and return the
degraded response, the breaker opens, and subsequent calls return in effectively zero milliseconds
because no network is touched. The captured timings in
`docs/evidence/step8-circuit-breaker-timings.txt` show this directly: calls 1–3 take 42–54 ms while
retrying, calls 4 and 5 return in 0.0–0.1 ms with the breaker open, and call 6 succeeds in 4.1 ms
once the dependency recovers and the reset timeout has elapsed. The matching event stream records
three `DEPENDENCY_FAILURE` events, one `CIRCUIT_OPENED` and one `CIRCUIT_CLOSED`.

## 5. How security events are collected

Every service imports one shared module, `libs/common/events.py`, and emits every security-relevant
occurrence as a single-line JSON object written to stdout, where Docker collects it. Nothing else
in the codebase writes an event, so the schema cannot drift service by service.

**The schema is fixed and enforced.** Every event carries thirteen fields: `eventId`, `timestamp`,
`serviceName`, `eventType`, `severity`, `userId`, `sourceIp`, `endpoint`, `httpMethod`,
`statusCode`, `message`, `correlationId` and `affectedEntity`. Extra fields are rejected and a
missing required field raises rather than emitting a partial event, because a silently malformed
event stream would only be discovered in Phase 2.

**What is captured.** `AUTH_SUCCESS` and `AUTH_FAILED` from `auth-service`; `UNAUTHORISED_ACCESS`
and `RATE_LIMIT_EXCEEDED` at the gateway; `REQUEST_RECEIVED` and `REQUEST_COMPLETED` from every
service; `INCIDENT_CREATED` and `INCIDENT_ESCALATED` from `incident-service`; `ASSET_ACCESSED` when
a `CRITICAL` asset is read; and `DEPENDENCY_FAILURE`, `CIRCUIT_OPENED`, `CIRCUIT_CLOSED` and
`SERVICE_ERROR` for failure conditions.

**Events are correlated across services.** Kong mints an `X-Correlation-ID` when the client does
not supply one and passes it through unchanged when it does; every service reads that header and
stamps it onto each event it emits. One analyst workflow therefore produces one traceable thread
across all three services. `docs/evidence/step12-correlated-logs.jsonl` holds 17 correlated events
from a single run of `client/demo_workflow.py`, all sharing correlation ID
`corr-332de1db16a547a4`.

**This feeds Phase 2 directly.** The schema was taken from the Phase 2 specification before any
service was written, so the SOC collector and knowledge-graph loader consume this stream with no
translation layer. Each event type already maps to a detection rule: `AUTH_FAILED` to multiple
failed logins, `UNAUTHORISED_ACCESS` to unauthorised endpoint access, `RATE_LIMIT_EXCEEDED` to
abnormal request rate, and `DEPENDENCY_FAILURE` with the circuit-breaker events to service failure.
