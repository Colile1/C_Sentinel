# Security event schema — the contract

**Status: FIXED at build step 3. Changing a field name after that is a breaking change to every
service and to all of Phase 2.**

Every security-relevant thing that happens in this system is emitted as one JSON line in this exact
shape, by `libs/common/events.py` and by nothing else. This schema is taken directly from the
Phase 2 specification so that Phase 1's output is Phase 2's input without translation.

## Fields

| Field | Type | Required | Notes |
|-------|------|----------|-------|
| `eventId` | string | yes | `evt-<uuid4 hex, 12 chars>` |
| `timestamp` | ISO-8601 string | yes | UTC, generated by the library, never by the caller |
| `serviceName` | string | yes | `auth-service`, `incident-service`, `asset-service`, `api-gateway` |
| `eventType` | enum | yes | See the table below |
| `severity` | enum | yes | `LOW`, `MEDIUM`, `HIGH`, `CRITICAL` |
| `userId` | string \| null | where known | The subject of the JWT, or the attempted username on a failed login |
| `sourceIp` | string \| null | where known | Client IP as forwarded by the gateway |
| `endpoint` | string | yes | The path, e.g. `/api/v1/incidents` |
| `httpMethod` | string | yes | |
| `statusCode` | integer | yes | |
| `message` | string | yes | Human-readable, one sentence |
| `correlationId` | string | yes | From `X-Correlation-ID`; generated when absent |
| `affectedEntity` | string \| null | where known | e.g. `incident-42`, `asset-7`, `login-endpoint` |

Extra fields are rejected. A missing required field raises rather than emitting a partial event —
a silently malformed event stream is worse than a loud failure, because Phase 2 discovers it weeks
later.

## Event types and where each is emitted

| `eventType` | Emitted by | Trigger | Feeds Phase 2 rule |
|-------------|-----------|---------|--------------------|
| `AUTH_SUCCESS` | auth-service | Valid login | baseline |
| `AUTH_FAILED` | auth-service | Bad credentials | Rule 1 — multiple failed logins |
| `UNAUTHORISED_ACCESS` | api-gateway | 401/403 on a protected route | Rule 2 — unauthorised endpoint access |
| `RATE_LIMIT_EXCEEDED` | api-gateway | 429 from the rate-limiting plugin | Rule 3 — abnormal request rate |
| `REQUEST_RECEIVED` / `REQUEST_COMPLETED` | all services | Every request, in and out | baseline and rate analysis |
| `INCIDENT_CREATED` | incident-service | New incident, carrying its severity | "creation of a high-priority incident" |
| `INCIDENT_ESCALATED` | incident-service | Severity raised to HIGH or CRITICAL | escalation signal |
| `ASSET_ACCESSED` | asset-service | Read of a CRITICAL asset | "access to sensitive asset" |
| `DEPENDENCY_FAILURE` | incident-service | A call to asset-service failed after retries | Rule 4 — service failure |
| `CIRCUIT_OPENED` / `CIRCUIT_CLOSED` | incident-service | Breaker state change | Rule 4, and the pattern demo |
| `SERVICE_ERROR` | all services | Unhandled 5xx | Rule 4 |
| `HEALTH_CHECK_FAILED` | SOC collector, from Consul (named for the failing service) | A service's Consul health check is critical | Rule 4 — service failure |

## Worked example

```json
{
  "eventId": "evt-9f2c41ab7d10",
  "timestamp": "2026-09-07T10:45:00Z",
  "serviceName": "incident-service",
  "eventType": "UNAUTHORISED_ACCESS",
  "severity": "HIGH",
  "userId": "user-14",
  "sourceIp": "192.168.1.25",
  "endpoint": "/api/v1/incidents/42",
  "httpMethod": "GET",
  "statusCode": 403,
  "message": "User attempted to read an incident outside their role scope",
  "correlationId": "corr-8842",
  "affectedEntity": "incident-42"
}
```

## Why this matters in Phase 1

This schema is what makes the data useful for SOC monitoring and knowledge-graph analysis: every
service already obeys it, so the collector, the detection rules and the graph loader consume the
stream with no translation layer. It is the short answer to "how are security events captured?".
